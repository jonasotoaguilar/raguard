> **Phase**: sdd-explore | **Date**: 2026-08-06 | **Author**: Jonathan Soto (jonasotoaguilar)
> **Status**: Ready for proposal — recommended next MVP slice, validated against repository evidence, archived changes, OpenSpec main specs, and ADR-0002/0005 action items.
> **Artifact store**: hybrid (OpenSpec + Engram, topic key `sdd/mvp-chat-citations/explore`)
> **Execution mode**: auto | **Delivery strategy**: auto-chain (stacked-to-main) | **Review budget**: 800 lines/session, 400-line PR gate

## Executive Summary

Retrieval is complete and archived (`mvp-retrieval-rrf`, PR #11): `POST /api/search` fuses tenant-filtered FTS + pgvector with deterministic RRF, gated on `chat.use`, with neutral empty results and cross-tenant isolation gates. What does **not** exist anywhere: a chat adapter (ADR-0005 mandates one and none exists), a prompt builder, a citation verifier (ADR-0002 action item #3 is still open), any `conversations`/`messages` tables (migrations are only 0001/0002), and any chat route. The smallest coherent API-first slice that delivers the PRD's headline feature — a trustworthy answer grounded in authorized chunks with **verifiable citations** — is **`mvp-chat-citations`**: `POST /api/chat` that resolves the request scope, reuses the archived retrieval path (extracted into a shared function so `POST /api/search` and `POST /api/chat` are one retrieval path per ADR-0002), skips generation entirely when there is no authorized evidence, builds a grounded prompt with retrieved chunks as **untrusted data**, calls a new narrow `ChatCompleter` adapter (OpenAI only for MVP, protocol ready for Anthropic per ADR-0005), and verifies every cited chunk id against the exact authorized retrieved set before returning. **Recommended: request-scoped chat in this slice** — zero migration, zero retention-policy commitment, fully reversible (persistence becomes an additive follow-up slice). Forecast: ~950–1150 changed lines across a stacked chain of ~4 PRs, each ≤ 400 lines.

## Current State

- **Retrieval is done and archived.** `apps/api/src/raguard_api/retrieval/` ships `contracts.py` (`Candidate`/`FusedResult`), `fusion.py` (`rrf_fusion`, k=60), `queries.py` (`build_keyword_query` `plainto_tsquery('simple', :query)` + `build_semantic_query` cosine `<=>` with `max_distance` bound + `build_ef_search_statement`), `embeddings.py` (`OpenAIEmbedder`), and `router.py` (`create_retrieval_router` → `POST /api/search`). Verify report (corrected tree) recorded **302 non-e2e tests passing**, 11/11 retrieval spec scenarios compliant, and 8/8 RRF mutations killed. The retrieval route handler currently **embeds the orchestration inline** (`_keyword_candidates`/`_semantic_candidates` helpers + `rrf_fusion`), so chat cannot compose it without an extraction refactor.
- **Authorization seam is ready and already gating retrieval.** `AuthorizationScope` (frozen: `tenant_id`, `user_id`, `capabilities`) provides `tenant_predicate(column)` (bound parameter, never a literal) and `has_capability()`. `AuthorizationResolver.resolve()` runs a fresh query per request (role changes apply immediately). `CHAT_USE = "chat.use"` already gates `POST /api/search`; `member` and `admin` both hold `chat.use` + `corpus.view` (`authorization/capabilities.py`, `MEMBER_CAPABILITIES`). The `require_capability` dependency pattern exists in both the documents and retrieval routers.
- **Error envelope is standardized.** `errors.py`: `{error: {code, message, details?}}` with 400/401/403/404/409/503; validation details allowlisted to `loc`/`type`/`msg` only; `ServiceUnavailableError` (503) is the dependency-failure convention used by retrieval for provider failure.
- **Provider adapter pattern exists for embeddings only.** `Embedder` protocol + `FakeEmbedder` live in shared `documents/contracts.py`; the API has its own `OpenAIEmbedder` in `retrieval/embeddings.py` (lazy client through injectable `client_factory`, bounded timeout, `max_retries=0`, 1536-dim validation). **There is no chat/completion adapter anywhere** — the `openai>=1.40,<3` package is already a direct API dependency (chat completions available with no new dependency), and `.env.example` already carries an unused `ANTHROPIC_API_KEY` placeholder ("backs the planned chat adapter" per README). ADR-0005 action items #1–#3 (define the two adapter interfaces; implement OpenAI chat; prompt assembly outside adapters with injection-hardening tests) are all open.
- **Citation verification is mandated and unimplemented.** ADR-0002 action item #3: "Implement citation verification as a post-generation check in the chat path." ARCHITECTURE runtime flow specifies: build prompt (retrieved chunks only, content as data) → generate → **verify every citation resolves to an authorized retrieved chunk** → return answer + citations. DESIGN.md §Citations & Source Preview makes citations strictly API-driven: the API returns answer + a `citations` array (chunk ids, document references, excerpt, position); the UI never invents, reorders, or reconstructs citations; an empty `citations` array triggers an explicit "No verified sources found" honesty notice. DESIGN.md §Data Fetching lists the chat contract point as "chat (answer + citations)".
- **Chat history is unbuilt and the retention decision is open.** No `conversations`/`messages` tables exist (only migrations `0001_identity_tables.py`, `0002_documents_chunks.py`); ARCHITECTURE's ERD *plans* them (`messages.citations jsonb` as the provenance ledger) but notes "Chat-persistence details ... depend on the open product decision on chat history." PRD §10 lists "Chat history: persistence scope (per-conversation, per-tenant) and retention policy" as open; ARCHITECTURE open decision #1 has "Persist conversations/messages per tenant; retention policy pending"; DESIGN's working assumption is persist per tenant with list/delete.
- **No chat code exists.** `rg` over `apps/api/src/` finds `chat` only in `identity/models.py` (capability allowlist) and `authorization/capabilities.py` (token). No `chat` module, no prompt builder, no spec under `openspec/specs/` (five main specs: tenant-identity, jwt-authentication, authorization-rbac, documents, retrieval).
- **Slice chain (from archived `mvp-authz-foundation` exploration, updated)**: A `mvp-authz-foundation` ✅ → B `mvp-document-ingestion` ✅ → C `mvp-retrieval-rrf` ✅ → **D `mvp-chat-citations` (this change)** → E `mvp-eval-harness` → F `mvp-web-ui`. The chain description for D: "chat orchestration, provider adapters, citation verification" (depends on A + C).

## User / Product Problem

PRD acceptance criterion: "A user can ask a question and receive an answer grounded in retrieval, with citations linking back to source chunks." PRD invariants: every citation must resolve to a retrievable chunk the user is authorized to access; retrieval-level filtering happens **before** generation; prompt-injection protection is tested with adversarial documents. KPI 1: ≥ 80% of eval-set questions answered with at least one verifiable citation. The problem *this slice* solves: documents are ingested and retrievable, but no answer can be produced — the product's headline capability (a trustworthy, verifiable answer) does not exist yet. This is the first slice where the **citation invariant** (PRD §5) and ADR-0002's post-generation verification are exercised by real code.

## Approaches

1. **Request-scoped chat slice with shared-retrieval refactor (`mvp-chat-citations`)** — `POST /api/chat` accepts `{query}` (plus optional `top_k` reuse), resolves a fresh `chat.use`-gated scope, retrieves via the shared retrieval function (same tenant predicates, same RRF, same fake in tests), skips generation when evidence is empty (neutral response, no provider call), builds a grounded prompt with retrieved chunks as untrusted delimited data, calls a new `ChatCompleter` (OpenAI, bounded timeout/retries), parses `[n]` citation markers, verifies every cited chunk id ∈ the retrieved set, and returns `{answer, citations}` via the standard envelope. Zero migration; zero retention commitment.
   - Pros: delivers the PRD headline feature end-to-end on the existing authorization invariant; ADR-0002 action item #3 and ADR-0005 action items #1–#3 all advance; no schema risk; reuses the embedder/error/router conventions; request-scoped keeps the PRD retention gap open without blocking; the shared-retrieval refactor tightens the "single retrieval path" invariant (both routes literally call one function).
   - Cons: introduces a generation provider call into the request path (latency/cost/key — mitigated by adapter + fakes in tests, e2e-only real calls); multi-turn follow-ups are not carried (no persistence); refactor of the archived retrieval router carries a small regression risk (guarded by existing integration tests); Medium-High effort vs the 800-line session budget — sdd-tasks forecasts a stacked chain.
   - Effort: Medium–High
2. **Chat slice with minimal conversations/messages persistence included** — add migration 0003 (`conversations`, `messages` with `citations jsonb`), models, and conversation/thread routes alongside `POST /api/chat`.
   - Pros: matches ARCHITECTURE ERD and DESIGN's working assumption; enables deep links (`/chat/$conversationId`) and follow-up context now.
   - Cons: commits to a retention-shaped schema while the PRD retention policy is still open (reversibility cost); adds migration + models + 2–3 routes, pushing the slice well past the 800-line session budget and almost certainly past 4 chained PRs; follow-up context requires history-aware prompt building (more prompt surface, more injection surface); retention/deletion semantics (ARCHITECTURE #1/#2) unresolved.
   - Effort: High (and budget-breaking)
3. **HTTP-compose chat** — `POST /api/chat` internally calls `POST /api/search` over HTTP to get chunks, then generates.
   - Pros: no retrieval refactor.
   - Cons: internal HTTP round-trip duplicates authz resolution and error mapping; couples the two routes at the network layer; a second code path for retrieval weakens ADR-0002's single-path invariant; slower; harder to test.
   - Effort: Low (but architecture-divergent)
4. **Defer chat; build the evaluation harness (E) first** — measure answer/citation quality before shipping generation.
   - Pros: quality measurement exists before the headline feature ships.
   - Cons: the harness's citation-verifiability metric has nothing to measure (no chat endpoint exists); the archived chain and both prior explorations validated chat before eval; violates "smallest version that works end to end"; the PRD KPI targets are confirmed *at harness setup* precisely so the harness calibrates later.
   - Effort: n/a — blocked

## Recommendation

**Approach 1 — the request-scoped chat slice `mvp-chat-citations`.** Evidence, not convention: (1) every prerequisite is shipped and archived — retrieval with tenant predicates and neutral empties (C), the `chat.use` capability (A), the `Embedder`/`FakeEmbedder` contract, the error envelope, and the isolation-gate test pattern; (2) ADR-0002 action item #3 (citation verification) and ADR-0005 action items #1–#3 (chat adapter interfaces, OpenAI implementation, prompt assembly with injection-hardening tests) are exactly this slice; (3) request-scoped chat requires **zero migration** and makes no commitment on the open retention decision — the smallest reversible choice; (4) the only structural change is a behavior-preserving extraction of the retrieval orchestration into a shared function, guarded by 12 existing integration cases, which strengthens the single-retrieval-path invariant; (5) eval (E) and UI (F) both consume this endpoint. Endpoint shape: `POST /api/chat` with request `{query}` and response `{answer, citations: [{chunk_id, document_id, document_name, position, content}]}`. Capability gate: `chat.use` (consistent with `POST /api/search`; both member and admin hold it). No-evidence contract: retrieval empty (no-match == empty corpus, identical neutral) → **skip generation** and return `{answer: null, citations: []}` (200), giving the UI its designed "No verified sources found" honesty state and spending zero provider tokens.

## Scope Boundaries

### In Scope (this change)

- `chat` API module: contracts (`ChatRequest` bounded query/top-k; `ChatResponse` with `answer` + `citations`; `Citation` = chunk_id, document_id, document_name, position, content), `ChatCompleter` protocol + `OpenAICompleter` (lazy client factory, bounded timeout, `max_retries=0`, bounded `max_tokens`), `FakeCompleter` + `_FailingCompleter` for tests.
- `POST /api/chat`: JWT-scoped, `chat.use`-gated, tenant only from the verified `tid` claim; reuses the shared retrieval function (tenant predicates before ranking, RRF, top-k bound); prompt builder keeps the system prompt static and injects retrieved chunks as delimited untrusted data (LLM01/LLM07: no secrets in prompts, no instruction merging); generation failure → bounded retries → 503 envelope, **never** a fallback to ungrounded generation; no-evidence → 200 neutral `{answer: null, citations: []}` with no provider call.
- Citation verification (ADR-0002 #3): parse `[n]` markers from the model output; **every** cited id MUST be a chunk id in the exact retrieved set the prompt was built from; resolve each to `Citation` metadata; a citation outside the set → reject the whole response via the error envelope (no partial answer, no persisting/rendering — per ADR-0002 "rejected before persisting/rendering"). Citation count bounded; missing markers → empty `citations` array is legal (UI honesty notice).
- Shared-retrieval refactor: extract the retrieval orchestration into a public function in the `retrieval` module; `POST /api/search` behavior stays byte-identical (existing integration tests must pass unchanged).
- Settings: `chat_model` (default `gpt-4o-mini` — config value for design phase), `chat_max_output_tokens`, `chat_retries` (bounded), `chat_max_query_length` (or reuse retrieval bound), `anthropic_api_key` placeholder; startup bounds validation.
- Tests: unit (citation verifier membership/parse/bounds, prompt builder isolation, contracts, settings bounds, completer contract via fake client); integration (route contract 200/400/403, no-evidence neutral + no provider call, provider failure 503 without partials, adversarial document cannot inject instructions, cross-tenant chat isolation release gate, citation membership invariants); e2e credential-gated provider smoke (`OPENAI_API_KEY`), never part of ordinary runs. Strict TDD, `uv run pytest -m 'not e2e'`.
- Security/release gates extended: adversarial-document chat scenario and cross-tenant chat isolation as first-class cases (extends the isolation-gate pattern; PRD acceptance criterion "tested with adversarial documents").

### Out of Scope (explicit, later slices)

- Conversations/messages persistence, history routes, multi-turn follow-up context, retention/deletion policy (open product decisions; request-scoped keeps them unblocked and reversible). The response contract is designed so a future `conversation_id`/history addition is additive.
- Anthropic chat adapter (protocol supports it per ADR-0005; `anthropic` dependency deferred), streaming/SSE (DESIGN non-goal), rate-limit policy values (ARCHITECTURE #7; only request bounds ship here).
- Evaluation harness (E), web UI (F), per-document grants, PostgreSQL RLS, document deletion semantics, worker changes, any migration.
- Any change to `PRD.md`/`ARCHITECTURE.md`/`DESIGN.md`/ADRs.

## Risks

| Risk | Mitigation |
|---|---|
| Shared-retrieval refactor regresses `POST /api/search` | Behavior-preserving extraction; the 12 existing retrieval integration cases and unit query tests must pass unchanged; refactor lands in its own PR before the chat endpoint |
| Generation provider latency/cost/model theft (LLM10) | `ChatCompleter` adapter + fakes in tests; bounded timeout, `max_retries=0`, `chat_max_output_tokens`; query bounds; no-evidence path makes zero provider calls; e2e-only real calls; rate-limit policy values surfaced (ARCHITECTURE #7) |
| Prompt injection via documents (LLM01) | System prompt static and secret-free (LLM07); retrieved chunks injected as delimited untrusted data; output treated as untrusted (LLM05) — citations parsed defensively; adversarial-document integration test is a release gate (PRD) |
| Citation parse fragility / hallucinated citations (LLM09) | Post-generation verification is the control, not the parse: any id outside the retrieved set rejects the response; empty citations remain a legal honest state; eval harness (E) later measures verifiability (KPI 1) |
| Chat slice size vs 800-line session / 400-line PR budget (`auto-chain`) | sdd-tasks forecasts a stacked chain; natural units: (1) contracts + verifier + prompt builder + settings + unit tests, (2) completer + shared-retrieval refactor, (3) chat endpoint + wiring + route integration, (4) isolation/adversarial/citation gates + e2e smoke |
| Sensitive disclosure through generation (LLM02) | Generation sees only the authorized retrieved chunks (retrieval-level filtering is the primary control); citations only reference those chunks; response omits tenant ids and provider details |
| Unbounded follow-up context / no streaming | Out of scope by design; request-scoped answers are standalone (DESIGN non-goal for streaming) |
